## 关键结论：页边界必须卡在 uc_stack 与 vregs 之间

`sys_rt_sigreturn()` 的恢复顺序决定了方案成立的条件：

```
restore_fpsimd_context()   512B 拷到 vregs (铺伪 waiter, 高地址)
restore_altstack()         读 uc_stack      (低地址, 造成缺页窗口)
```

4.14 实测：`uc_stack` 在帧内 `+0x90`，`vregs` 在 `+0x260`，帧长 `0x480`。
要让 `uc_stack` 落在被打掉的文件映射页、`vregs` 留在下一页：

```
frame_start & 0xFFF = 0x220   (则 frame_end 页内 0xda0)
  uc_stack 页内 0xe30  -> 低页, MAP_FIXED 打掉
  vregs    页内 0x1000 -> 高页, 保留
```

对应 `ss_size ≈ 0x10230`；模块从 `0x10000` 起自动校准到该同余类。
推导过程与校验方法见 `tools/lane11_layout.md`。

## 真机第一轮验证（零风险，建议先跑这个）

```sh
# 1. 推送 (与既有部署流程一致)
adb push build/ionstack_preload.so /data/local/tmp/
adb push build/ionstack_perf_target /data/local/tmp/

# 2. 只验证帧布局, 不触发消费、不写内核
adb shell "LD_PRELOAD=/data/local/tmp/ionstack_preload.so \
  IONSTACK_STAGE=lane11-check /data/local/tmp/ionstack_perf_target"
```

期望看到：

```
lane11 store ready path=/data/local/tmp/erblk size=0x400000
lane11 altstack calibrated size=0x10230 pgoff=0x220 attempt=N
stage-lane11-check ... ok=1
```

`ok=1` 说明 4.14 帧布局推导在本机成立 —— 这一步**不会** panic。

若 `calibrated` 那行显示 `pgoff` 收敛不到 `0x220`，说明厂商栈帧与推导有差异，
把实际 `pgoff` 记下来即可定位问题（模块会打印每次 attempt 的实测值）。

## 下一步（需要真机）

1. **确定 `L11_WAITER_IDX`**：`vregs` 内伪造 waiter 的 qword 下标。
   这是唯一仍需实测收敛的参数（参考项目对应 `DELTA`/`iov_off`）。
   先用 `IONSTACK_LANE11_WAITER_IDX=N` 覆盖，配合 `lane11-check` 观察。
2. **接入消费**：把 `l11_setup_altstack()` 与 `slide_consumer_thread()` 的
   `sched_setattr` 编排成"铺栈 -> 立即消费"，替换 `prepare_good_kernel_page()`
   的 perf 依赖。注意参考文档的时序纪律：
   - 读 `DELTA` 环境变量必须在等待 `w_done` **之前**
   - 铺完栈后到消费之间**不得有任何 syscall**（会改栈）
3. **`selinux_state.enforcing` 偏移**仍标 `[VERIFY]`，需真机确认。

## 风险提示

写好原语之前，任何一次错误的 `iov`/`IDX` 猜测都可能 panic 重启。
按参考项目做法，先只跑 `lane11-check`（安全），再逐步放开消费。
